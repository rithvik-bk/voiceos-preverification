01What it is, in one picture

Put a bodyguard between you and the voice assistant. Before the assistant is allowed to actually do anything, the bodyguard asks one question — and only lets it through if the answer is good.

The one question the bodyguard asks about every action is:

the one question

"Did the user actually say this — or did the AI make it up, mishear it, or grab it from somewhere sketchy?" If it traces back to what you said → let it through. If not → stop, and ask you one quick thing.

02Why it needs to exist

Today you'd happily say "set a timer" or "text mom." You would never say "pay my invoices" or "wire the vendor." Not because the assistant can't — because you don't trust it. One wrong payment is permanent, and you'd never use it again.

04How the check physically happens

This is the part that actually matters. We're going to follow one sentence — "Send $54.79 to Dan" — from your mouth to the money, and watch exactly where a wrong number can sneak in, and where the check catches it.

First: your words pass through two AIs before anything happens

People picture the assistant "hearing you and doing it." It doesn't. Your sentence goes down a pipeline, and two separate neural networks rewrite it along the way. Preflight is the one box in this pipeline that is not a neural network.

the fact everything hinges on

The LLM does not copy your number into the action. It reads a transcript and re-generates the action one token at a time, by sampling the most-likely next piece of text. The 54.79 that comes out the other end is a number the model re-typed — not your bytes. Almost always right. Occasionally a digit off. On a payment, "occasionally" is unacceptable — so we check.

So what world actually turns 54.79 into 54.99? (your question)

It's not random. There are exactly four ways it happens, and it matters which — because three of them slam straight into Preflight, and one of them doesn't (that one is a different layer's job, and we say so out loud):

Model re-typing drift. The tokenizer chops 54.79 into pieces; when the model regenerates it, it samples a wrong digit. Pure fumble.
caught
Context contamination. Another number was nearby — an invoice on screen said $54.99 — and the model grabbed that one instead of what you said.
caught
Injection. Text it read — an email, a webpage — literally said "pay 54.99," and the model obeyed the page instead of you.
caught
ASR misheard the audio itself. "seventy-nine" sounded like "ninety-nine," so the transcript already says 54.99. Preflight compares to the transcript, so it can't see this one.
not caught

The honest line — the one Kai will respect: Preflight catches every case where the transcript kept your number but the action didn't (drift, contamination, injection). A true mishear, where the transcript is already wrong, is caught by a different mechanism — the ASR's own confidence score and a spoken read-back — not by this layer. We don't pretend one box does everything.

The check itself: indexOf, not intelligence

Here's the physical thing that happens inside the blue box — no model, no network, no judgment. It gets two inputs and runs plain string/number code over them:

Step by step, all of it plain code:

  • Normalize. Turn "$54.79" into the number 54.79; turn spoken "fifty-four seventy-nine" into 54.79 with a fixed number-words grammar. A rule table, not a model.
  • Search. For amount = 54.99, scan the transcript's numbers — {54.79}. Is 54.99 in there? No. → amount_not_in_speech. For who = "Dan", scan the words for "Dan" (exact match, or off-by-one typo). Found → record which span licensed it.
  • Decide. Every routing value found a home → fire. Any one didn't → hold and ask. That's the whole verdict.

Every one of those steps is indexOf, an editDistance, or a number compare. A person could run it by hand with a highlighter and get the same answer. Same inputs → same output, every single time. That is precisely why it is not "an AI checking an AI": there is no second model, no opinion, nothing to hallucinate — just a comparison you could verify yourself.

One more piece: not every value gets this treatment

The action has parts, and they're not equally dangerous. The check only guards the ones that can hurt you.

07"Wait — isn't this just AI checking AI?"

No — and this is the part Kai cares about most. There is no second AI anywhere in the check. The bodyguard is a rulebook: it compares the value to your words and looks up where it came from. Same input always gives the same answer, forever.

what we are NOT doing

A guessing machine grading a guessing machine — still a guess.

what we ARE doing

A fixed rule, checkable by hand, reproducible on any laptop.

So when Kai asks "how do I know it's right?" — he can run it himself and get the identical answer every time. That's proof, not a second opinion.

08"Doesn't all this checking slow it down?"

No — because there's no AI and no internet in the check, just a quick comparison. We measured it: about 5 millionths of a second per action. The action itself (actually sending the message) takes seconds. The check is invisible on the clock.

09The tree — finally

You said you never saw a tree. Right — because a tree only appears for big tasks, and everything so far was one action.

one action

"Text Dan." → one check. No tree needed.

a big task = many actions

"Do my whole inbox." → 40 actions. The tree is just this checklist.

Here's a real example. You say: "Go through my inbox, find every lead, reply to each, message the right people, and email me a report." That's one instruction that becomes many steps. The tree is the map of those steps, each marked before anything runs:

The one subtle rule that makes big tasks possible and safe

In a big task, steps feed each other — and that creates the twin cases below. Same shape, opposite verdict. This is the cleverest part, and the one to be able to say cold:

passes ✓

"Email the lead you found."

Step 1 searched and returned a lead, and showed it to you. That's a result (rung 2). It's allowed to become the next step's destination.

blocks ⛔

"Pay the address in that email."

Step 1 read an email body. That's read-text (rung 4). It can fill a message but can never become a destination — so paying it is impossible by rule.

the whole trick, one line

A value the assistant looked up as a result can be trusted onward; a value it merely read as text can never become a destination — no matter how many steps it passes through.

10Where we started vs. what it became

the original project

The bodyguard for one action. Check a single action before it fires: mishears, wrong person, injected destination. This is built and tested — it already answers Jonah's and Kai's asks.

what it became

The bodyguard for a whole autonomous task. The same check, run across a 40-step tree, so the assistant can safely do big real work while you walk away. This is the capability jump — from "send one email" to "run my morning."

11The whole thing in one breath

Every action has to show where it came from before it's allowed to happen.

A destination must trace to you, never to something the AI just read. Across a big task, a result it looked up can hand off to the next step — but read-text can never become a destination. It's a fixed rulebook, not a second AI, and it runs in millionths of a second. That's what lets voice safely go from "send one text" to "run my whole morning."
