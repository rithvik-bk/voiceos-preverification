SECTION 0The one job, in a sentence

A voice assistant hears you, then does things — sends a message, issues a refund. Preflight is a small, deterministic checkpoint that sits at the last inch, right before an action fires, and asks one question: does every important detail of this action actually trace back to something you said? If yes, it fires untouched. If not, it holds and asks one question — or, for an injected value, blocks outright.

SECTION 1Why a tool call goes wrong in the first place

To understand what Preflight guards against, you have to see that your words pass through two neural networks before an action happens, and the second one doesn't copy your details — it re-generates them.

SECTION 2The core idea: provenance

Every value in an action has a source — where it came from. Preflight ranks sources, and refuses to let a dangerous value come from a weak source. This ranking is the whole intellectual core; everything else is plumbing around it.

Two words you'll see everywhere in the code:

  • Routing parameters — who / where / how-much. A wrong one causes harm (money to the wrong person). These must trace to a licensed source.
  • Content parameters — the words of a message. A wrong one is awkward, not catastrophic. These are never blocked; they're surfaced for you to see (disposition SURFACE).

SECTION 4The seven verdicts (the reason codes)

The gate can only ever return one of these outcomes. This table is the literal contents of core/src/codes.ts — the single authoritative list. Knowing it cold means you know everything the system can decide.

Wire codeCanonical nameVerdictWhat it means
provenance_mismatchPF_INJECTION_ROUTING_FROM_CONTENTBLOCKA destination/amount slot resolved to a value whose only source is read content — the injection firewall. Can't be fixed by asking, so it's a hard block.
insufficient_provenancePF_ROUTING_RANK_TOO_LOWBLOCKA routing value's source ranks below the routing minimum (screen/model can never license routing). The other face of the firewall.
amount_not_in_speechPF_AMOUNT_NOT_IN_SPEECHHOLDThe amount isn't in the spoken number-set (e.g. 54.99 ∉ {54.79}). A hard inequality — no tolerance. Money ⇒ confirm.
misbound_paramPF_MISBOUND_PARAMHOLDBoth values were spoken, but they trace to different clauses — the pairing is crossed ("refund Dan $50 and Sarah $30" → refund Dan $30).
ambiguous_targetPF_AMBIGUOUS_TARGETHOLDTwo or more real targets match the spoken name; needs exactly one. (Ask which.)
target_not_foundPF_UNGROUNDED_ROUTING_PARAMHOLDA routing value resolves to nothing real — hallucinated or misheard target. Also the indirect wrong-tool catch.
missing_parameterPF_MISSING_PARAMETERHOLDA required field is blank (a structural malformed-call check).

A PASS is simply the absence of any of these. Content parameters get a fourth disposition, SURFACE — they fire but the discrepancy is shown, never hard-blocked.

SECTION 6Inside core, file by file

This is the brain. The files form a pipeline: turn speech into searchable spans → know what targets exist → resolve a spoken name to a real target → run the gate → emit a receipt. Here's the data flow, then each file.

The pipeline files

provenance.ts
The source-rank lattice from Section 2. Defines Source, SourceKind, the ranks (RANK), and the minimum rank each parameter class requires (minRankFor, bestRank). The rulebook for "where is a value allowed to come from."
transcript.ts
finalizeUtterance(id, text) turns your spoken sentence into a FinalizedTranscript — the words as positioned spans the gate can search. attributeToTranscript answers "does this value appear in the transcript, and where?"
grounding.ts
GroundingStore — the session's memory of what really exists (your channels, contacts, customers) and how each was learned (its source). rememberTargets(targets, source) is how a tool result gets admitted to the pool.
resolve.ts
resolveTarget maps a spoken name to a real target using fuzzy matching (editDistance, normalizeLoose/normalizeTight). Returns a Resolution with 0 candidates (→ not-found), 1 (→ good), or many (→ ambiguous).
licensing.ts
licensingDescriptor — given a resolution and its sources, computes what actually licenses a parameter: the bridge between "we found a target" and "is its source strong enough?"

The gate itself

gate.ts
The heart, ~470 lines. preflight(call, contract, store) walks every parameter in the tool's contract: content params are consent-surfaced; routing params are resolved, rank-checked, and slot-checked (a destination demands a transcript span = the firewall; an amount runs the number-twin check). Then it runs the misbinding pass. It returns a Receipt, or throws a PreflightBlock with a reason code. runGate wraps that in a plain {verdict:'pass'|'block'} object.
misbinding.ts
assertCoClausal — when two or more routing params each ground, it checks they came from the same clause. Catches the crossed pairing ("refund Dan $50 and Sarah $30" fired as refund Dan $30). Emits misbound_param.
codes.ts
The seven-verdict registry from Section 4 — wire code, canonical PF_* name, disposition, and a summary. Also documents in-code what is structurally out of scope (ASR mishear, direct wrong-tool).
receipt.ts
emitReceipt → a PreflightReceipt: for every parameter, the value and the source that vouched for it. The audit trail — proof of why an action was allowed.
shadow.ts
shadowGate / ShadowLog — OBSERVE mode: record what the gate would have blocked, without blocking anything. How you roll out safely and gather real data before enforcing.
block.ts
PreflightBlock, the typed error the gate throws, plus requiredText, the required-field extractor behind missing_parameter.
index.ts
The public front door — the single list of everything core exports.

enforced, not just claimed

core/test/enforcement.test.ts is a test that fails the build if any code path in core imports a network or LLM library. "No AI, no network" isn't a promise in a README — it's a test.

SECTION 7Inside contracts

The gate needs to know, for each tool, which parameters are routing and which are content — and which routing params are dangerous slots (destination, amount). That knowledge lives in annotation files, one per integration.

catalogs/slack.annotations.json
A second catalog, proving the format generalizes beyond one product.
src/lint.mjs
The linter — validates every catalog against the format so a write/destructive tool can't ship un-annotated (which would be fail-open). Run by the tests.
FORMAT.md
The human spec for the annotation format.

SECTION 8Inside the adapter (how it plugs into VoiceOS)

core is pure logic; the adapter is how it actually rides along inside VoiceOS. VoiceOS launches custom tools as small local stdio MCP subprocesses — so Preflight ships as one of those, wrapping each tool call.

withPreflight.ts
The wrapper. Takes a tool handler and returns a guarded one: build the context, run the gate, and on a block return a repair instead of firing. The seam between VoiceOS and core.
server.ts
The stdio MCP server itself — the process VoiceOS spawns and talks to.
context.ts
Assembles what the gate needs for a call — the current transcript + the grounding store — from what crosses the MCP boundary.
runtime.ts
The per-call runtime that drives OBSERVE vs ENFORCE and threads the verdict back.
repair.ts
Turns a block into a single spoken repair line ("You said $54.79 — which amount?") — Jonah's error-handling concern, answered by riding the assistant's existing revise loop.
receipt.ts / bin.ts / index.ts
The adapter-side receipt emitter, the executable entry point, and the exports.
OBSERVE

The gate runs and logs what it would block. Nothing changes for the user. You gather real data and prove the false-block rate before touching behavior.

ENFORCE

The gate actually holds/blocks. You switch to this only once OBSERVE shows it's safe. Rollout is a config flag, not a rewrite.

See docs/INTEGRATION.md for the exact wiring, including the one small change on the VoiceOS side (handing the transcript to the tool-call context) that unlocks the full checks.

SECTION 9Inside eval — the part that makes Kai nod

A safety layer is worthless if you can't prove how often it's right. eval measures the gate against labeled cases and reports honestly. This is the rigor half — the answer to "no AI grading AI, and don't just tell me it works, show me."

corpora/self · blind · replay
Three sets of labeled cases (cases.json). Self = generated from the gate's own shadow log; blind = written independently to probe capabilities; replay = drawn from real traffic shapes. Reported separately — never blended into one flattering number.
src/runner.ts
Loads a corpus and runs every case through the real gate, collecting the verdicts.
src/adapter.ts
The capability-honest scorer. If a case needs something core doesn't implement yet, it's scored NOT-RUNNABLE-YET with the missing capability named and counted — never quietly turned into a fake pass or a fake catch.
src/report.ts
Renders one table per corpus: catch-rate, false-block-rate. Contains no cross-corpus aggregation — and the tests assert its absence, so a blended number can't sneak in.
src/catalog.ts · schema.ts · fixturegen.ts · cli.ts
Catalog loading, the case schema, the fixture generator (grows new test cases from the shadow log), and the command-line entry (requires an explicit --timestamp — no hidden clock, so runs are reproducible).

the honesty is the feature

The design choice that impresses a rigor person isn't a high score — it's that the harness refuses to fake one. Unrunnable cases are counted as unrunnable, out loud. That's the opposite of a demo that hides its failures.

SECTION 11End-to-end: one call through every file

Follow "refund Dan $54.79" where the model re-types the amount as $54.99. This is exactly how the files connect.

  1. transcript.ts — finalizeUtterance turns your sentence into spans: [refund][Dan][$54.79].
  2. grounding.ts — the session already remembered your customers from a list-read: Dan, Sarah (source: tool_output).
  3. The model proposes refund(recipient="Dan", amount="54.99"). The adapter's context.ts packages the call + transcript + store and withPreflight.ts hands them to the gate.
  4. gate.ts — parameter recipient (a destination slot): resolve.ts matches "Dan" to the real customer; it carries a transcript span → licensed.
  5. gate.ts — parameter amount (an amount slot): normalize → 54.99; is it in the spoken number-set {54.79}? No. → throw PreflightBlock('amount_not_in_speech').
  6. codes.ts — that code maps to disposition HOLD and name PF_AMOUNT_NOT_IN_SPEECH.
  7. repair.ts — turns it into one spoken line: "You said fifty-four seventy-nine — which amount should I refund?"
  8. receipt.ts — records the whole decision (recipient ✓ by span, amount ✗ not in speech). The action never fired. You answer, it re-checks, it sends the right number.

The clean case is the same path with a happy ending: amount="54.79" is in {54.79} → no block → the receipt is emitted → the refund fires with zero added friction. That "fires instantly when correct" behavior is as important as the catch — it's the proof Preflight isn't a nag.

SECTION 13Honest scope — what it does and doesn't do

Being precise about the edges is what makes the whole thing trustworthy. Say these before anyone asks.

it catches
  • Model drift (a re-typed wrong value)
  • Injected / read-from-content destinations
  • Ambiguous targets (two "Dan"s)
  • Hallucinated targets you never said
  • Amounts you never spoke
  • Crossed pairings (misbinding)
it does not catch
  • A true ASR mishear — if the transcript is already wrong, the gate faithfully grounds the wrong words. That's a read-back-confirmation problem, a different layer. Stated in codes.ts; no fake reason code invented for it.
  • A wrong tool where every parameter happens to ground — caught only indirectly.

The one honest todo

The single non-passing test is a deliberately marked todo, not a failure: a "confused-deputy launder," where a step copies a tainted value into a structured output without declaring where it came from. Catching that needs value-level dataflow from the executor — outside the pure pre-verification layer. It's named in the tests rather than hidden.

The multi-step prototype (plan.ts, compose.ts, taint.ts, autonomy.ts)

The repo also contains a working prototype that extends the single-action check across a multi-step plan (verify each step's provenance, propagate "taint" so a value read from content can never become a later destination, and an autonomy dial). It is a prototype — it demonstrates where the idea goes; it is not wired into a live product, because multi-step autonomy isn't something VoiceOS ships today. It's in the repo for completeness, not as a claim of shipped capability.
